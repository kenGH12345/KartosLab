## 0. 复杂度粗判与协作模式

### 0.1 复杂度粗判

| 维度 | 判定 | 依据 |
|---|---|---|
| 涉及端 | **多端**（通用层 + circuit + color_vision） | 三组件进 `lib/common/`，2 pilot 各自接入 screen 与 scenario model |
| 文件影响 | **>10 文件** | 3 新组件 + 2 scenario model 扩展 + 2 screen 接入 + ≥4 JSON + ≥5 测试 |
| 数据/Schema | **字段增减** | scenario JSON 加可选 `inquiryTask`/`challenge` 顶层字段（向后兼容） |
| 架构影响 | **局部调整** | 新增通用组件到 `lib/common/widgets/`（L1 候选登记）；不改 solver/物理核心（N2） |
| 跨端交互 | **有但清晰** | 2 pilot 复用同一组通用组件 API；字段路径已读代码锁定（见 §5.1 T2） |

**结论：`medium`。**

**判定理由**：三组件 API 设计 + JSON schema 扩展是本需求核心，且 spec 已给出非常详细的 schema 定义与 AC 验收项；2 pilot 接入点的字段路径已通过阅读源码确认（非"需大规模代码探索"）。未达 `complex`（无新增/重写模块，物理引擎不动，knowledge_panel 不改）。

### 0.2 协作模式建议

**推荐 `SubAgents`（委派 frontend-leader 细化两个 pilot screen 接入）**。

依据：
- 本工程为**纯 Flutter 单语言**工程，无独立"后端"角色；`ScenarioManagerBase` 已是通用层（scenario 解析扩展属前端数据 model 层），不适用 backend-leader。

> ⚠️ 用户确认：本判定为 `medium` + 委派 frontend-leader 细化，如用户认可可按此推进；如需 tech-leader 独立完成全部（`TechLeader only`），本方案已含完整可执行任务清单，可直接执行。

## 3. 三组件 API 设计（通用层 `lib/common/widgets/`）

### 3.1 输入数据模型（`lib/common/widgets/inquiry_models.dart`）

三组件共享的**纯数据模型**，与 scenario JSON `inquiryTask` 字段 1:1 映射。放独立文件，使三个组件都能 import 而不产生循环依赖。

```dart
/// 探究任务数据模型（对应 scenario JSON `inquiryTask` 顶层字段）
/// 由各 sim 的 scenario model 在 fromJson 时解析并持有。
@immutable
class InquiryTask {
  final String question;                       // 核心探究问题（inquiryTask 存在则必填）
  final List<InquiryStep> steps;               // 分步指引（可空）
  final String? referenceConclusion;           // 参考结论（null = 无对照功能）
  final List<InquirySnapshotColumn> snapshotColumns; // 实验记录表列定义（可空 → sim 默认提供）

  const InquiryTask({
    required this.question,
    this.steps = const [],
    this.referenceConclusion,
    this.snapshotColumns = const [],
  });

  factory InquiryTask.fromJson(Map<String, dynamic> json) => InquiryTask(
    question: json['question'] as String,
    steps: (json['steps'] as List<dynamic>? ?? const [])
        .map((e) => InquiryStep.fromJson(e as Map<String, dynamic>))
        .toList(growable: false),
    referenceConclusion: json['referenceConclusion'] as String?,
    snapshotColumns: (json['snapshotColumns'] as List<dynamic>? ?? const [])
        .map((e) => InquirySnapshotColumn.fromJson(e as Map<String, dynamic>))
        .toList(growable: false),
  );
}

@immutable
class InquiryStep {
  final String id;          // 步骤唯一标识
  final String instruction; // 步骤指引
  final String? hint;       // 可选提示

  const InquiryStep({required this.id, required this.instruction, this.hint});
  factory InquiryStep.fromJson(Map<String, dynamic> json) => InquiryStep(
    id: json['id'] as String,
    instruction: json['instruction'] as String,
    hint: json['hint'] as String?,
  );
}

/// 实验记录表列定义。source 区分参数(param)与读数(reading)两类。
@immutable
class InquirySnapshotColumn {
  final String key;    // 对应 snapshotProvider 返回 Map 的 key
  final String label;  // 表头显示文字
  final String source; // 'param' | 'reading'
  const InquirySnapshotColumn({required this.key, required this.label, this.source = 'reading'});
  factory InquirySnapshotColumn.fromJson(Map<String, dynamic> json) =>
    InquirySnapshotColumn(
      key: json['key'] as String,
      label: json['label'] as String,
      source: json['source'] as String? ?? 'reading',
    );
}
```

**设计要点**：
- `InquiryTask` 等纯数据类放 `lib/common/widgets/inquiry_models.dart`，使三个组件共同引用、避免重复定义。
- `snapshotColumns` 缺失时（空列表）由组件 fallback 到「序号/时间戳」基础两列（见 §3.2），不强制 JSON 必须提供。

### 3.3 ExperimentLogger（`lib/common/widgets/experiment_logger.dart`）

```dart
/// 快照提供者回调：各 sim 提供当前「参数 + 读数」快照 Map。
/// key 需与 ColumnDef 的 key 匹配。
typedef SnapshotProvider = Map<String, dynamic> Function();

/// 表格列定义（供表头渲染）。
@immutable
class ColumnDef {
  final String key;    // 对应快照 Map 的 key
  final String label;  // 表头显示
  final bool isParam;  // true=参数列，false=读数列（用于视觉区分）
  const ColumnDef({required this.key, required this.label, this.isParam = false});
}

/// 实验记录器：学生手动快照当前实验状态，累积对比数据。
/// 数据仅内存（session 级）· 不持久化（spec A1）。
class ExperimentLogger extends StatefulWidget {
  const ExperimentLogger({
    super.key,
    required this.columns,          // 列定义（表头）
    required this.snapshotProvider, // 快照提供者
    this.maxRows = 20,              // 容量上限（默认 20，AC-1.6）
    this.compact = false,
    this.onExport,                  // 预留导出回调（本轮不实现 · T1 决断见 §5.1）
  });

  final List<ColumnDef> columns;
  final SnapshotProvider snapshotProvider;
  final int maxRows;
  final bool compact;
  final VoidCallback? onExport;     // 预留 · null = 不显示导出按钮
}

class _ExperimentLoggerState extends State<ExperimentLogger> {
  // 内存表格数据：每行 = {index, timestamp, ...columns keys 对应的快照值}
  List<Map<String, dynamic>> _rows = [];

  // 行数 ≥ maxRows 时：拒绝新增并提示「记录已满，请清空最早记录」
  // 操作：记录本次实验（新增行）· 删除单行 · 清空全部
}
```

**状态管理**（≤20 行快照 · 清空/删除/导出）：
- `_rows` 为 State 持有内存列表（session 级，spec A1）。
- **记录**：点「记录本次实验」→ 调 `widget.snapshotProvider()` 取当前快照 Map → 追加一行（首列序号 + 时间戳 + 各 column key 值）。若 `_rows.length >= widget.maxRows` → 拒绝并提示「记录已满，请清空最早记录」（AC-1.6）。
- **删除单行**：行尾删除按钮 → removeAt(index)。
- **清空全部**：清空按钮 → `_rows.clear()`。
- **导出**：`widget.onExport == null` 时不渲染导出按钮（T1 决断，见 §5.1）。

**表格渲染**：`Table` 或 `DataTable`（compact 模式用 `Table` 更紧凑，适配九宫格 bottomCenter 窄条）。首列固定「#」序号 + 第二列「时间」。列头来自 `widget.columns` 的 label，单元格取值 `row[key]`。

AC-1.4 满足：import 仅 `package:flutter/material.dart` + `ColumnDef` 自含。

### 3.4 ConclusionPanel（`lib/common/widgets/conclusion_panel.dart`）

```dart

/// 阶段② 对照：参考结论 + 学生结论并排（参考结论展开后不可收回）

// _submitted = true  → 阶段②（对照）

class _ConclusionPanelState extends State<ConclusionPanel> {
  final TextEditingController _ctrl = TextEditingController();
  bool _submitted = false;

  void _submit() {
    // 至少输入非空才可提交；提交后 _submitted = true → 展开参考结论 + 学生结论
  }
  void _reSubmit() {
    // 学生可修改结论再次提交（阶段② 内编辑学生结论，参考结论仍保持可见）

```

**行为规则**（回指 spec §2.4）：
- **提交前**：只显示输入框 + 提交按钮；`referenceConclusion` **不渲染**（AC-1.7 · "结论先消失"）。
- **提交后**：`_submitted = true` → 参考结论文本展开 + 学生已输入结论并排显示。`_submitted` 一经 true 不可回退（参考结论不可收回）。
- **再次编辑**：阶段② 提供「修改结论」按钮 → 展开学生结论编辑框 → 再次提交更新（参考结论保持可见，不重新收起）。
- `widget.referenceConclusion == null` → 无对照功能，仅保留自由输入 + 提交（阶段② 退化为仅显示学生结论），AC-1.7 中"参考结论"相关规则自然不适用。

AC-1.4 满足：import 仅 `package:flutter/material.dart`。

### 3.5 三组件是否合并为 `InquiryWorkflow` 容器？—— **取舍决断**

**决断：本轮不预抽 `InquiryWorkflow` 容器，三组件保持独立。**

| 方案 | 取舍 |
|---|---|
| **独立三组件（推荐）** | 生命周期/状态各自独立（ExperimentLogger 内存行 / ConclusionPanel 两阶段各自 State）；可单独复用；可单独测试。spec §2.4 明确"若 referenceConclusion 缺失则隐藏对照"，ExperimentLogger 也独立可配（可无 logger 场景），合并会引入不必要的耦合。 |
| 合并 `InquiryWorkflow` | 紧耦合：三组件必须一起出现，无法单独复用任一能力；且 spec 已留出"某些组件可独立隐藏"的弹性（无 inquiryTask 不显示、无 referenceConclusion 不显示对照），容器会把这些弹性写死。 |

**组合方式**：各 sim 在 screen 层用 `Column`（或 NineGridLayout 边格）自行组合三组件即可，无需通用容器。若未来出现 ≥2 sim 采用相同组合布局，再按 3-Time Rule 评估上抽 `InquiryWorkflow`（登记为 L1 未来候选，本轮不做）。

```dart
    timeLimit: (json['timeLimit'] as num?)?.toInt() ?? 30,
    timeBonusPerLevel: (json['timeBonusPerLevel'] as num?)?.toInt() ?? 5,
    accuracyThreshold: (json['accuracyThreshold'] as num?)?.toDouble() ?? 95.0,
    targets: (json['targets'] as List<dynamic>? ?? const [])
        .map((e) => CVTargetColor.fromJson(e as Map<String, dynamic>))
        .toList(growable: false),
    randomTargets: json['randomTargets'] != null
        ? CVRandomTargets.fromJson(json['randomTargets'] as Map<String, dynamic>)
        : null,
  );
}

@immutable
class CVTargetColor {
  final String color;   // 形如 "#FFFF00"
  final String label;   // 如 "黄色（红+绿）"
  // fromJson: color/label 必填
}

@immutable
class CVRandomTargets {
  final bool enabled;
  final int count;
  final bool excludeGrayscale;
  // fromJson
}
```

**向后兼容**（AC-2.3）：`challenge`/`inquiryTask` 均可选；null 时 sim 按旧逻辑（见 §4.3 fallback）或传统模式运行。

### 4.3 挑战模式 JSON 驱动化（`rgb_bulbs_screen.dart` 改造 + fallback）

**T3 决断：需要 deprecation 日志。** 在 `_MagicLabScreenState.initState` 中，若 `widget.scenario?.challenge == null` 且进入挑战模式，打 `debugPrint('DEPRECATED: challenge config missing for ${scenario.scenarioId}, using hardcoded fallback')`。理由：低成本高价值——便于识别仍依赖旧硬编码的 scenario 以规划后续清理，且不阻塞渲染（N8 明确不删旧逻辑，仅标记 deprecated）。

改造点（对应 spec §4.2 表格 + AC-4.x）：

| 改造点 | 现状 | 目标 |
|---|---|---|
| 目标色来源 | `_randomColor()` 硬编码 | `challenge.targets` 按序 → 用尽后 `randomTargets` 随机 |
| 倒计时 | `30 + (level-1)*5` 硬编码 | `challenge.timeLimit + (level-1)*challenge.timeBonusPerLevel` |
| 精度阈值 | `99.99` 硬编码 | `challenge.accuracyThreshold` |
| 难度反馈 | 无 | `difficulty == easy/medium/hard` → 决定是否显示 RGB 数值提示 |
| successCriteria 统一 | 脱钩 | 挑战完成触发 `checkObjectives` |

**fallback 策略**（AC-4.5）：
```dart
// 读取挑战配置，缺省时回退旧硬编码
CVChallengeConfig? _cfg() => widget.scenario?.challenge;

// 目标色：有 targets 则按序；否则 fallback _randomColor()
Color _nextTargetColor() {
  final cfg = _cfg();
  if (cfg != null && cfg.targets.isNotEmpty) {
    // targets 未用完 → 按序取；用完且有 randomTargets.enabled → 随机
  }
  return _randomColor(); // fallback 旧逻辑
}

// 倒计时：有 cfg → cfg.timeLimit + (level-1)*cfg.timeBonusPerLevel；否则 30+(level-1)*5
// 精度：有 cfg → cfg.accuracyThreshold；否则 99.99
```

**挑战完成触发 `checkObjectives`**（AC-4.4）：`ColorVisionScenarioManager` override `checkObjectives`（当前基类返回 true，color_vision_scenario_manager.dart 未 override）。在挑战成功的 `showCelebrationDialog` 分支回调处，调用 `manager.checkObjectives(state)` 判定 `successCriteria`（rgb-make-white.json 已有 `colorMatch` 型 criterion）。需要一个 `CVCriterionConfig.check(ColorVisionState)` 实现（当前 `CVCriterionConfig` 仅有数据无逻辑，需补 `check` 方法按 type 判定的最小实现）。

#### snapshotProvider 从哪个 model 读取（T2 决断 · 已读代码确认字段路径）

已确认字段来源：
- `SolvedCircuit.currentFor(id)` / `voltageFor(id)` / `brightnessFor(id)`（`circuit_state.dart` L233-236）—— 提供电流(A)/端电压(V)/灯泡亮度。
- `CircuitComponent.value`（`circuit_state.dart` L51）—— 提供元件参数值（电阻 Ω / 电池电压 V）。
- 元件 id 来自 `simple-series.json`：`res_1`（电阻）、`bulb_1`（灯泡）、`bat_1`（电池）。

circuit 的 snapshotProvider 实现（在 `_CircuitScreenState` 内构造）：

```dart
// 由 scenario JSON 的 snapshotColumns 驱动；列 key 对应以下 Map 的 key
Map<String, dynamic> _circuitSnapshot() {
  final res = _state.findComp('res_1');   // 电阻元件（simple-series 固定 id）
  final bulb = _state.findComp('bulb_1');
  final bat = _state.findComp('bat_1');
  return {
    'resistance': res?.value,            // 电阻(Ω) · param ← CircuitComponent.value
    'voltage': bat?.value,               // 电池电压(V) · param ← CircuitComponent.value
    'current': _solved.currentFor('res_1'),  // 电流(A) · reading ← SolvedCircuit.currentFor
    'brightness': _solved.brightnessFor('bulb_1'), // 灯泡亮度 · reading ← SolvedCircuit.brightnessFor
  };
}
```

**关于「电压」来源的补充说明**：spec 的 `snapshotColumns` 示例含 `{key: voltage, source: reading}`（期望读数电压）。simple-series 为单电池单回路，电池端电压约等于 `bat_1.value`（V），读 `_solved.voltageFor('res_1')` 可得电阻端电压。方案：snapshotColumns 中 `voltage` 的 `source` 标 `reading`，snapshotProvider 返回 `_solved.voltageFor('res_1')`（电阻端电压，更能体现"改变电阻→电流/电压变化"的探究主题）。**AC-2.4 需保证 JSON snapshotColumns 的 key 与 snapshotProvider 返回 key 一致。**
