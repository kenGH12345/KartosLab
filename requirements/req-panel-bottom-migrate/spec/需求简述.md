## 1. 背景

molarity 实验已完成操作面板底部横排试点（S1, S4）：

- `NineGridLayout` 新增 `footer` 参数（横跨整行底部控件条 · 高 = min(96, 屏高×0.16) · centerH 已扣除 footerH）
- 方案：`SingleChildScrollView(horizontal) + FittedBox(scaleDown) + Row[控件组]`
- 验收通过：320px 无溢出 + 1600px 合理 + 功能可达

本需求将该方案推广至其余屏，统一操作面板布局位置，释放中部空间给 sim 画面展示。（S2, S3）

### 3.2 optics 不迁移判定（S8）

**结论：optics 的 midRight 面板保留原位，不迁移至 footer。**

理由：
1. **性质差异**：optics 的 `_RightPanel` 是教学目标/约束条件**只读文本面板**，不是交互式控件组（滑块/下拉/按钮）
2. **阅读需求**：文本内容需要纵向阅读空间，footer 横排条（高 ≤ 96px）无法承载多行文本
3. **设计初衷**：footer 方案为"交互控件横排"设计（FittedBox scaleDown + Row 布局），文本面板不符合此模式
4. **用户认知**：midRight 文本面板不遮挡 sim 主要交互区域，保留不影响 G2 目标

- NineGridLayout.footer 参数本身的 API 改动（已就绪 · S4）

## 8. 风险

| # | 风险 | 影响 | 缓解 |
|---|------|------|------|
| R1 | 某些屏控件数量超过 molarity（如 rgb_bulbs 3 色滑块 + 模式切换），320px 下可能过于拥挤 | 功能不可达 | 允许 SingleChildScrollView(horizontal) 横向滚动作为降级；极端情况下可折叠/收起次要控件（S4） |
| R2 | circuit 工具条（电池/开关/灯泡图标 + 拖拽交互）迁到 footer 后拖拽目标区域变化 | 用户体验退化 | [待技术确认: circuit 工具条的拖拽交互在 footer 位置是否需要调整 hit test 区域]（S7） |
| R3 | 批次 4 复杂度高（非标准面板 + 遗留修复），可能超 30 分钟 | 进度延期 | 允许批次 4 拆为 4a（迁移）+ 4b（遗留修复）两个子批次 |
| R4 | 各屏 midRight 清除后可能影响 NineGridLayout 其他区域的空间分配 | 布局异常 | 每批迁移后立即运行 layout test 确认无回归 |
