## 1. 三项技术待确认项调研结论（PM 交接项）

### 1.1 待确认项 1：ScenarioManager 是否支持"按顺序加载多个场景"的钩子

**结论：不支持。且不存在任何序列 / 依赖 / 完成事件概念的 API。**

证据（`lib/common/scenario/scenario_manager_base.dart` 全文 121 行）：

| API | 行号 | 语义 |
|---|---|---|
| `loadScenarios()` | :80-102 | 读 manifest，把**全部场景并列**载入内存 List（单场景失败跳过） |
| `findById(id)` | :105-111 | 按 id 查找，无顺序语义 |
| `loadScenario(id)` | :114-120 | 单场景 → 构建域初始状态（TState），找不到抛异常 |
| `scenarios` | :77 | 不可变列表视图 |

无"当前场景"、无"下一场景"、无完成回调、无跨场景状态容器。各 sim 的场景切换由用户经 `ScenarioMenuButton` 手动触发（`lib/common/widgets/scenario_menu_button.dart`），完全自由跳转。

**对方案的影响**：方案 A（扩展 manifest）需要**改造 ScenarioManagerBase 解析层**（entry 新键 + 跨 entry 查询）；方案 B/C 则把 `loadScenario(id)` 当作干净的"节点进入"挂点直接调用——**后者零改动**，C5（走 ScenarioManager 加载体系）架构上天然成立。

### 1.2 待确认项 2：条件树（req-criteria-composable）API 契约是否已稳定

**结论：已稳定可用，剧本可直接引用其 JSON 契约与求值器注入模式；仅流程状态还挂在 4.closing（收尾中），核心 API 不会再动。**

证据：

- **API 全貌已固化**（`lib/common/scenario/success_condition.dart:30-248`）：sealed 树（`LeafCondition` / `AllCondition` / `AnyCondition` / `NotCondition`）+ `fromJson`（:37）+ `evaluate(leafEvaluator)` 递归求值（:105-106）+ `collectLeaves()`（:109）+ `allSatisfied`（:115-119）；深度上限 4、非法格式 fail loud 抛 `FormatException`（:40-59）。
- **已验证落地**：22 个单测 + 8 sim 全接入 + 全量 339 测试通过；commit `c0c861f` 已入库（2026-08-24）。[来源: requirements/req-criteria-composable/process.txt:10,16]
- **知识库已登记为通用组件**（候选 9，含接入模式 4 步 + 设计边界）。[来源: docs/knowledge/kratos-java-simulations/shared-abstraction-plan.md 候选 9]
- meta 状态 `in_progress / 4.closing`（`requirements/req-criteria-composable/meta.yaml:3-4`）——剩余为 svn 审批等收尾动作，非 API 变更。

**关键设计事实（PoC 引用方式的决定性约束）**：条件树是"**结构通用 + 叶子语义 sim 私有**"——叶子 `type` 的求值由各 sim 注入的闭包解释（`success_condition.dart:101-106` 注释明示）。因此剧本分支**不能直接复用** sim 级叶子枚举（如 `concentrationReached` 依赖 molarity 运行态），而应定义**剧本级叶子枚举**（`nodeCompleted` / `predictionScore` 等）+ 注入剧本级求值器——这是"复用结构、不复用语义"，恰好是该 API 的设计意图，无 breaking 风险。

**风险对冲**（对齐 notes.md 风险提示）：评估期内条件树发生 breaking change 的概率极低（已 commit + 339 测试锁定）；PoC 设计引用的是 JSON 契约（`{"all": [...]} / {"any": [...]} / {"not": {...}}`），即使内部实现微调也不影响剧本侧引用。

### 1.3 待确认项 3：现有 manifest.json schema 是否有扩展预留字段

**结论：没有预留字段，且 manifest 根本没有 schema 守卫；更糟的是 8 份 manifest 的 entry 结构已呈三种形态漂移。**

证据：

- **schemas/ 目录只有场景级 schema**：8 份 `<sim>_scenario.schema.json`（Glob 实测），无任何 manifest schema。
- **entry 三形态并存**：
  - circuit：`{id, file, name, description}`（`assets/scenarios/circuit/manifest.json:4-9`）
  - molarity：`{id, file}`，连顶层 `version` 都没有（`assets/scenarios/molarity/manifest.json:3`）
  - optics（平铺根目录）：`{id, name, level, domain}`——**无 `file` 字段**，文件名 = id 约定（`assets/scenarios/manifest.json:4-8`）
- **运行时只消费两个键**：`manifest['scenarios']` + `entryKey(entry)`（默认 `entry['id']`，forces 用 `entry['file']`）（`scenario_manager_base.dart:84-89,62`）。entry 上其余键被**静默忽略**——鸭子兼容：加新键不会 crash，但也**没有任何守卫防止结构漂移**。
- **生成链路与 manifest 耦合**：generate.py 会自动把生成场景写入 manifest（`scripts/ai_scenario_gen/generate.py:5-6` docstring）——manifest 结构变更必须同步 generate.py，且注释中已记录过因目录映射不一致产生死文件的事故（`generate.py:48-54`）。

**对方案的影响**：运行时层面扩展 manifest **可行**（新键被忽略）；但工程层面，在无 schema 守卫、三形态漂移、AI 工具链耦合的地基上叠加编排字段（方案 A），漂移与生成冲突风险显著——这是方案 A 的结构性负面证据。

## 2. E1 · 表达力缺口分析（AC1）

**审计目标**："老师编排完整课时"（如：40 分钟课时 = 3-5 个实验场景 + 预测验证 + 按表现分流 + 课时总结）。

**现状定性**：场景体系是"单场景孤岛"——ScenarioManager 逐 id 加载（§1.1），条件树只在**单场景内**判定 `successCriteria`（实证样例：`assets/scenarios/molarity/precision-dilution.json:29-42`，all+not 组合是场景内判定），场景间无依赖、无顺序、无分支、无状态流。8 sim 各自独立 manifest + schema，无跨 sim 层。

### 2.1 缺口清单（10 类，按教学时序编排链分组）

| # | 缺口类别 | 具体缺失 | 严重程度 | 当前 workaround |
|---|---------|---------|---------|----------------|
| G1 | **顺序编排** | 无序列表达：manifest `scenarios` 是并列注册表（无序），无 `next`/顺序语义；学生可任意跳场景 | **必须** | 老师口头/学案告知顺序；学生手动逐个选。无顺序保证 |
| G2 | **前置解锁** | 无场景间依赖："先完成 A 才能进 B"不可表达 | **必须** | 无（所有场景立即可选） |
| G3 | **条件分支** | 无"条件 → 路由到不同场景"机制；预测题得分数据已有通路（`PredictionPanel.onResultChanged`，`lib/common/widgets/prediction_panel.dart:31`）但只用于摘要展示（`inquiry_drawer.dart:340-341`），无消费方做路由 | **必须** | 无 |
| G4 | **完成信号不统一**（隐藏债务） | 场景"完成"事件源不齐：A 类 4 sim（molarity/color_vision/circuit/optics）判定已接线，但 **view 层真实消费仅 2 处**（circuit_screen + rgb_bulbs_screen）；B 类 4 sim（sound/radio_waves/wave_interference/forces）纯解析不判定。剧本"节点完成判定"依赖统一完成信号 | **必须**（对剧本而言） | 无——剧本需限定试点 sim 或先清债务。[来源: req-criteria-composable/process.txt:2,13；test/tooling/scenario_runtime_wiring_test.dart 豁免台账] |
| G5 | **跨场景状态传递** | 零数据流：`loadScenario` 每次全新构建 TState（`scenario_manager_base.dart:114-120`），上一场景的参数/测量结果不可带入下一场景（"第 1 题的测量值用于第 2 题"不可表达） | 重要 | 无。Phase 1 可不做（节点间传递"进度事件"而非"实验数据"），列为表达力边界 |
| G6 | **课时级进度追踪** | 无课时聚合：单场景有 GameRules 计分 + GameOverDialog（[来源: docs/knowledge/kratos/architecture/project-config.md §3]），但无"N 个场景总进度/总分" | 重要 | 无 |
| G7 | **跨 sim 编排** | manifest 按 sim 隔离（8 份），无跨 sim 结构；home_screen 硬编码 8 sim 入口（`lib/screens/home_screen.dart:59-150`），无"课时"入口概念 | 重要 | 无。"一节课跨 molarity + color_vision"不可表达 |
| G8 | **剧本级 AI 生成链路** | 三件套（`docs/prompts/<sim>_scenario.md` + `schemas/<sim>_scenario.schema.json` + generate.py）仅覆盖单场景；`_shared/` 附录 2 份均为场景级字段（combinable_criteria / inquiry_task） | **必须**（对 C2 而言） | 无。剧本 JSON 无法由现有链路生成/校验 |
| G9 | **重试 / 循环** | 无"未达标 → 重做本场景"循环边 | 锦上添花 | 学生手动退出重进（状态重置≈重做），但无"剧本要求重做"的表达 |
| G10 | **课时运行时导航 UI** | 学生侧无课时入口/进度指示（作者侧编排 UI 属 C4 禁区，但运行时最小进度 UI 是 runtime 必需——见 §8 C4 界定） | 重要 | 无 |

### 2.2 向后兼容性现状分析（AC9 前置）

- **场景资产持续增长**：需求文档口径 42 个场景；本报告实测 **46 个场景 JSON**（Glob `assets/scenarios/**/*.json` = 54 文件，含 8 份 manifest；其间有 req-single-bulb-inquiry 等新增）[来源: docs/knowledge/kratos-java-simulations/shared-abstraction-plan.md 候选 8 状态更新]。增长趋势本身要求兼容策略是"引用式"而非"侵入式"。
- **既有零改动兼容先例**：`inquiryTask` 可选顶层字段（缺失时 sim 传统模式运行）与 SuccessCondition 平铺格式零改动加载（[来源: shared-abstraction-plan.md 候选 8/9]）——项目已两次验证"可选字段/引用式"兼容模式，剧本层应延续第三例。
- **引用失效风险**：剧本引用 `scenarioId`，若场景改名/删除则剧本悬空——需要 fail loud + 降级策略（沿用 `FormatException → 单场景降级` 模式，`success_condition.dart:26-28`）+ 引用存在性守卫测试（沿用 `scenario_runtime_wiring_test.dart` 白名单/豁免台账模式）。

## 3. E2 · 候选方案对比（AC2 / AC8 / AC9）

三个候选：A 扩展现有 manifest（编排字段内嵌）/ B 新增 lesson-plan 编排层 / C 轻量 DSL·状态机引擎（覆盖需求文档列举的全部 3 个方向）。

### 3.1 方案 A：扩展现有 manifest.json

**核心思路**：在每 sim 的 manifest entry 上新增编排键（`requires` / `next` / `branch` 等），ScenarioManagerBase 扩展解析，编排语义分布于各 entry。

**数据结构草案**：

```json
{
  "scenarios": [
    { "id": "simple-series", "file": "simple-series.json",
      "requires": ["default"], "next": "parallel-bulbs",
      "branch": [ { "when": {...}, "to": "open-circuit-debug" } ] }
  ]
}
```

**与 ScenarioManager 关系**：侵入式——`loadScenarios` 解析层需识别新键并构建 entry 间依赖图。

**硬约束满足情况**：C2 **部分满足**（manifest 无 schema，AI 生成需先补 manifest schema——而统一三形态漂移本身是一块前置工程；且 generate.py 自动写 manifest 会与编排字段互相干扰）；C3 部分（场景 JSON 不动，但 8 份 manifest 需动且无守卫）；C5 满足；C4 满足。

**结构性缺陷**：
1. **跨 sim 课时无处安放**（G7 无解）：manifest 按 sim 隔离，"课时"跨 sim 时除非再造全局 manifest——那已是方案 B 的形态。
2. **职责错位**：manifest 是注册表/目录，编排是流程图。流程语义分布式地埋在每个 entry（每条 entry 要知道自己的后继），AI 生成**单个新场景**时会连带改写邻接 entry 的编排语义——与 generate.py 现有"追加 entry"行为直接冲突（§1.3）。
3. **无守卫的漂移地基**：entry 三形态已并存（§1.3），再叠编排键加剧漂移。
4. 线性顺序隐式依赖数组下标，AI 生成插入场景时易错位。

### 3.2 方案 B：新增 lesson-plan 编排层

**核心思路**：剧本是**引用既有场景的独立顶层资产**，与 scenario 完全解耦：

```
assets/lessons/<lesson-id>.json          ← 剧本（节点图：线性/分支/解锁）
assets/lessons/manifest.json             ← 课时注册表
schemas/lesson.schema.json               ← 剧本 schema（C2 三件套之一）
docs/prompts/lesson.md (+ _shared 附录)  ← 剧本 prompt（C2 三件套之二）
lib/common/scenario/lesson_plan.dart     ← 剧本数据模型（fail loud 解析）
lib/common/scenario/lesson_runtime.dart  ← 编排状态机（节点进入/流转/解锁/完成）
```

**数据结构草案**（详见 §5 PoC）：节点 = `{ id, title, scenario: {sim, scenarioId}, unlock?, advance? }`；`advance` 支持默认顺延 / 显式跳转 / 条件路由表；`unlock` 与路由条件均为**剧本级条件树**（复用 SuccessCondition 的 all/any/not JSON 契约，注入剧本级叶子求值器，见 §1.2）。

**与 ScenarioManager 关系**：**零改动**。LessonRuntime 持有目标 sim 的 ScenarioManager 实例，节点进入时调 `manager.loadScenario(scenarioId)` 构建 TState 交给 sim screen 渲染——C5 天然满足（剧本的场景加载就是 ScenarioManager 加载）。

**硬约束满足情况**：C2 满足（集中式单一 JSON + 封闭枚举的节点/叶子类型，三件套模式完整复制，`_shared` 附录机制可复用）；C3 满足（纯增量引用，46 个存量场景与 8 份 manifest 零触碰，非剧本场景独立运行不受影响）；C5 满足；C4 满足（剧本手写 + AI 生成；运行时仅学生侧最小进度 UI，非编排器——§8 界定）。

**代价**：新增一层 runtime 状态机 + 课时入口/进度最小 UI（工程量大于 A 的表面改动）；跨 session 进度持久化需独立决策。

### 3.3 方案 C：轻量 DSL / 状态机引擎

**核心思路**：设计通用状态机 DSL（`states` / `transitions` / `guards` / `actions`），剧本只是 DSL 的一个应用实例。

**与 ScenarioManager 关系**：同 B——引擎驱动节点 → `loadScenario`。

**硬约束满足情况**：C3/C5 满足；C2 **不满足倾向**（自由 DSL 的生成错误率随自由度上升，校验器复杂度同步上升，与 §C3 "prompt + schema + 样本即可生成"路线背道而驰）；C4 满足。

**结构性缺陷**：
1. **违背项目既定设计边界**：SuccessCondition 刚固化的设计哲学是"仅三个组合算子 + 有限嵌套深度，**不做自由 DSL**——枚举保证判定器可实现"[来源: shared-abstraction-plan.md 候选 9 设计边界；success_condition.dart 全文注释同义]。剧本分支上自由 DSL 等于推翻刚立的边界。
2. **Over-engineering**：教学课时编排需求收敛（线性 + 分支 + 解锁 + 可选重试），不需要图灵级通用引擎。
3. 调试/校验/文档成本最高。

**保留价值**：其显式 transition/guard 概念被方案 B 吸收为 `advance.routes` + `unlock`。

### 3.4 结构化对比（6 维度，AC2 要求 ≥5）

| 维度 | A 扩展 manifest | **B lesson-plan 层** | C DSL 引擎 |
|---|---|---|---|
| **表达力覆盖度** | 差：单 sim 内线性勉强；条件分支可拼装但脆弱；跨 sim（G7）无解 | **良**：线性/分支/解锁/跨 sim 全覆盖；循环（G9）可作后续叶子/路由类型枚举扩展 | 优（理论任意图），但对需求冗余 |
| **AI 可生成性（C2/AC8）** | 差：无 schema 地基 + 流程定义分布式（生成单场景连带邻接语义）+ generate.py 冲突 | **优**：集中式单一 JSON、封闭枚举类型、三件套模式复制；剧本只**引用**既有场景（无需生成物理正确数据），是 AI 生成友好度最高的资产类型 | 差：自由度↑→生成错误率↑→校验复杂度↑ |
| **实现复杂度** | 中（表面小、实际 = manifest schema 统一 + generate.py 改造 + 8 manifest 迁移） | 中（新层独立开发 ~12 人天，不动存量） | 高（引擎 + 校验器 + 调试） |
| **向后兼容性（C3/AC9）** | 中：场景 JSON 不动，但 manifest 必须动且无守卫 | **优**：纯增量引用，46 场景 + 8 manifest 零触碰 | 优：纯增量 |
| **可扩展性** | 差：编排语义困死在注册表 | **良**：节点 advance 类型 / 条件叶子类型沿 SuccessCondition 枚举扩展模式演进 | 优（但用不上） |
| **架构一致性**（加分维度） | 差：职责错位 + 与配置化演进路径相悖 | **优**：复用三大既有模式（ScenarioManagerBase 加载 / SuccessCondition 条件树 / AI 三件套 + `_shared` 附录） | 差：违背"不做自由 DSL"边界 |

## 4. E3 · 方案推荐（AC3）

### 4.1 推荐：方案 B——新增 lesson-plan 编排层

**推荐理由（引用 §3.4 对比结论）**：

1. **6 个对比维度中 5 维为优/良**，唯一相对劣势（新层工程量 12 人天）换来的是零存量触碰与三大既有资产的直接复用；方案 A 在 AI 可生成性（C2）与架构一致性两个**硬约束相关维度**均为最差，一票否决理由充分；方案 C 的表达力优势对本需求是冗余，而其 C2 违背与设计边界冲突是结构性缺陷。
2. **三大既有资产即插即用**（全部源码级实证）：`loadScenario(id)` 是干净的节点进入挂点（§1.1）；SuccessCondition 的"结构通用 + 叶子注入"设计意图正好容纳剧本级条件（§1.2）；`_shared` 附录 + generate.py 模式可直接复制为剧本三件套（§1.3）。
3. **notes.md 已确认发现 #4 的方向印证**："剧本层应是可选的上层编排，而非对现有 scenario 结构的侵入式修改"——方案 B 是该原则的直接实现。

### 4.3 与 AI 可生成化路线（§C3）的关系（AC8）

方案 B 的剧本 JSON 是**全项目 AI 生成友好度最高的资产类型**，理由：

1. **无需物理正确性**：场景生成要求 `initialParams`/`domain` 数据物理合理（8 份 prompt 各自沉淀了领域规则）；剧本只**引用**既有场景 id + 组合编排原语——生成的正确性边界仅是"引用存在 + 图结构合法"，二者均可被 schema + 加载期校验完全锁定。
2. **封闭枚举**：节点 advance 类型（`next`/`onCompleted`/`routes`）与条件叶子类型（`nodeCompleted`/`predictionScore`/`scenarioSuccess`）均为封闭枚举——延续 SuccessCondition"枚举保证判定器可实现"的边界，杜绝自由 DSL。
3. **三件套完整复制**：`schemas/lesson.schema.json`（结构约束）+ `docs/prompts/lesson.md`（编排原语说明 + 课时教学法 few-shot）+ generate.py `--lesson` 模式（校验后写入 `assets/lessons/` 并更新 lessons manifest）；跨 sim 的场景 id 清单可由脚本从 8 份 manifest 自动提取注入 prompt 上下文（防引用幻觉）。

**三种编排模式的表达位置**：

| 模式 | 表达方式 | 示例位置 |
|---|---|---|
| **线性序列** | `advance: {type: "onCompleted", to: ...}` 显式跳转；（设计备选 `{type: "next"}` = nodes 数组顺延，适合纯线性课时） | n1 → n2 |
| **条件分支** | `advance: {type: "routes", routes: [{when: 条件树, to}, ...]}`——`when` 是**剧本级条件树**（本例叶子 `predictionScore`，依赖预测题得分）；无 `when` 的末项为兜底路由 | n2 → n3-challenge / n3-review |
| **前置解锁** | `unlock: 条件树`（本例叶子 `nodeCompleted`）——**手动跳转门禁**：未解锁节点灰显/不可进；与 `advance` 职责正交（unlock 管可见性，advance 管自动流转） | n2/n3-*/均含 unlock |

**剧本级条件叶子枚举**（封闭枚举，v1 仅 3 类——复用 SuccessCondition 的 all/any/not 组合契约包裹）：

| 叶子 type | 语义 | 依赖 |
|---|---|---|
| `nodeCompleted` | 指定节点已完成 | 剧本 runtime 自身进度状态（**无外部依赖**） |
| `predictionScore` | 指定节点的预测题答对数/正确率 达到阈值（`metric: count/ratio`，`operator: gte/lte`） | **req-predictive-inquiry**：数据源为 `PredictionPanel.onResultChanged(verified, correct)`（`prediction_panel.dart:31`），经 InquiryDrawer 可选转发接线（R3） |
| `scenarioSuccess` | （可选增强）指定场景的 successCriteria 曾全满足 | **req-criteria-composable**：SuccessCondition 判定链（A 类 sim 接线） |

### 5.2 核心运行逻辑伪代码

```dart
// ========= 伪代码（设计稿，非实现 · C1）=========
// 依赖：LessonPlan（assets/lessons/<id>.json 解析产物）
//       managers: sim -> ScenarioManagerBase 子类实例（复用各 sim 既有单例）

class LessonRuntime {
  LessonPlan plan;                                  // 剧本（fail loud 解析）
  Map<String, ScenarioManagerBase> managers;        // 各 sim 场景管理器（复用）
  Set<String> completed;                            // 已完成节点（进度状态）
  String current;                                   // 当前节点 id
  Map<String, ({int verified, int correct})> predictionResults;  // 预测题结果
  bool lastScenarioSuccess;                         // 当前场景 successCriteria 状态

  // ---------- 1. 剧本加载 ----------
  Future<void> load(String lessonId) async {
    // 读 assets/lessons/<lessonId>.json（lessons manifest 注册）
    // fail loud：entry 缺失 / 节点引用的场景不存在（findById==null）/
    //           路由目标悬空 / 图不可达 → FormatException → 课时级降级（不 crash）
    plan = LessonPlan.fromJson(await readLessonJson(lessonId));
    current = plan.entry;
    enterNode(current);                             // C5：场景加载走 ScenarioManager
  }

  // ---------- 2. 节点进入（节点切换） ----------
  void enterNode(String nodeId) {
    final node = plan.find(nodeId);
    if (node.scenario == null) { onLessonCompleted(); return; }   // 终点节点
    final manager = managers[node.scenario.sim];
    final state = manager.loadScenario(node.scenario.scenarioId); // ← 复用既有 API（§1.1）
    // 渲染 sim screen（携带 runtime 钩子注入）：
    //   onScenarioSuccess : 场景 successCriteria 全满足事件（A 类 sim 判定链）
    //   onPredictionResult: PredictionPanel.onResultChanged 转发（R3 接线）
    renderSimScreen(node, state, hooks: this);
  }

  // ---------- 3. 事件源 ----------
  void onScenarioSuccess() {            // 依赖 req-criteria-composable 判定链接线
    lastScenarioSuccess = true;
    completed.add(current);
    advanceFrom(current);               // 完成判定 → 触发流转
  }

  void onPredictionResult(String nodeId, int verified, int correct) {
    predictionResults[nodeId] = (verified: verified, correct: correct);
  }   // 依赖 req-predictive-inquiry（onResultChanged 通路）

  // ---------- 4. 流转判定（advance 求值） ----------
  void advanceFrom(String nodeId) {
    final node = plan.find(nodeId);
    switch (node.advance.type) {
      case 'next':        enterNode(plan.nextInOrder(nodeId));       // 线性顺延
      case 'onCompleted': enterNode(node.advance.to);                // 显式跳转
      case 'routes':                                              // 条件分支
        for (final r in node.advance.routes) {
          if (r.when != null && evaluateCondition(r.when)) { enterNode(r.to); return; }
        }
        enterNode(node.advance.routes.last.to);              // 兜底路由（无 when 项）
    }
  }

  // ---------- 5. 条件求值（复用 SuccessCondition 结构 + 剧本级叶子求值器） ----------
  bool evaluateCondition(SuccessCondition cond) {
    return cond.evaluate((type, params) => lessonLeaf(type, params));
  }   // ← 直接复用 req-criteria-composable 的 evaluate(leafEvaluator) 注入模式（§1.2）

  bool lessonLeaf(String type, Map<String, dynamic> params) {
    switch (type) {
      case 'nodeCompleted':   return completed.contains(params['nodeId']);
      case 'predictionScore':
        final r = predictionResults[params['nodeId']];
        if (r == null || r.verified == 0) return false;       // 未作答 → false（fail-safe）
        final v = params['metric'] == 'ratio' ? r.correct / r.verified : r.correct;
        return compare(v, params['operator'], params['threshold']);
      case 'scenarioSuccess': return lastScenarioSuccess;
      default: return false;   // 未知叶子类型一律 false（沿用"未知 type 一律 false"语义）
    }
  }

  // ---------- 6. 解锁门禁（手动跳转时） ----------
  bool isUnlocked(String nodeId) {
    final unlock = plan.find(nodeId).unlock;
    return unlock == null || evaluateCondition(unlock);
  }

  // ---------- 7. 课时完成判定 ----------
  bool get lessonCompleted =>
      plan.requiredNodes.every(completed.contains);   // requiredNodes = 非终点全部节点
}
```

**运行主循环（4 步契约，对齐 AC5）**：**剧本加载**（`load`，fail loud + 课时级降级）→ **当前节点判定**（`enterNode` + 事件源挂接）→ **节点切换**（`advanceFrom`：next / onCompleted / routes 三型）→ **完成判定**（`onScenarioSuccess` 节点级 + `lessonCompleted` 课时级）。
