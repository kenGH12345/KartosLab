# 需求文档：教学剧本——多场景流程编排评估

> **需求 ID**: req-lesson-scripting  
> **类型**: 评估型立项（evaluation）  
> **SOP**: deep-vibe  
> **版本**: v1.0（2026-08-24）  
> **状态**: 需求定义完成，待进入技术评估阶段

---

## 1. 背景与目标

### 1.1 业务背景

当前 KratosLab 的场景体系是"单场景孤岛"架构（S2, S7）：

- 每个 scenario JSON 描述一个独立实验（含 domain/ui/initialLayout/inventory/constraints/objectives）
- ScenarioManager 逐 id 加载，场景间无依赖、无顺序、无分支关系
- 8 个 sim 各有独立的 scenario schema + manifest，无跨 sim 编排层

**核心缺口**（S1）：不能表达——
1. "先完成 A 解锁 B"（场景解锁/前置条件）
2. "根据预测题得分分支到不同场景"（条件分支）
3. "一节课的实验序列"（课时级线性/图状流程）

这是面向"老师编排完整课时"目标的**最大表达力缺口**。

### 1.2 评估目标

本需求**不直接实现 runtime**，而是产出评估报告，服务于两个目的（S8）：

| 目的 | 说明 |
|------|------|
| **立项决策依据** | 明确"是否启动剧本 runtime 开发"的 go/no-go/defer 判断所需信息 |
| **路线图规划输入** | 确定剧本功能在产品路线图中的排期位置、前置条件依赖关系 |

### 1.3 依赖基础现状

| 依赖能力 | 关联需求 | 状态 | 说明 |
|----------|---------|------|------|
| 条件判定 | req-criteria-composable（S5） | 4.closing | 条件树（all/any/not）+ 计分配置化 → 剧本分支判定基础 |
| 预测题得分 | req-predictive-inquiry（S6） | 3.iteration | predictions 选项式预测题 → "按得分分支"依赖此能力 |
| 做中学工作流 | req-inquiry-learning（S4） | 4.closing | 通用组件已落地 → 剧本是课时级延伸 |
| AI 场景生成 | req-ai-scenario-toolchain-lite（S3） | — | §C3 AI 可生成化路线 → 剧本 JSON 需延续此约束 |

## 2. 功能范围（评估范围）

本需求的"功能"是**产出一份评估报告**，报告应覆盖以下评估维度：

| # | 评估维度 | 产出要求 |
|---|---------|---------|
| E1 | 表达力缺口分析 | 系统梳理当前 scenario 体系在"多场景编排"方面的能力边界，列出具体缺口清单 |
| E2 | 候选方案设计 | ≥ 2 个候选方案的对比（如：扩展现有 manifest / 新增 lesson-plan 层 / DSL 引擎等），含优劣分析 |
| E3 | 方案推荐 | 明确推荐一个方案，给出推荐理由 |
| E4 | PoC 设计 | 推荐方案附带最小 PoC 设计——伪代码 + JSON 结构示例（不实现代码） |
| E5 | 工作量估算 | 推荐方案的粗粒度估算（方案级人天 + 关键假设），PoC 部分不估时 |
| E6 | 前置条件与排期建议 | 明确哪些依赖需先完成、建议的路线图排期位置 |

## 3. 详细功能描述

### 3.1 E1 - 表达力缺口分析

**目标**：对当前 scenario 体系做系统性能力审计。

**要求**：
- 以"老师编排完整课时"为目标场景，列出所有表达力缺口
- 缺口应分类（如：顺序编排、条件分支、状态传递、进度追踪、循环/重试等）
- 每个缺口需标注严重程度（必须/重要/锦上添花）和当前 workaround（如有）
- 需覆盖已有 42 个场景 JSON 的向后兼容性分析

### 3.2 E2 - 候选方案设计

**目标**：提出 ≥ 2 个可行方案。

**要求**：
- 每个方案需描述：核心思路、数据结构草案、与现有 ScenarioManager 的关系、对 §C1-§C4 配置化硬约束的满足情况
- 方案对比维度至少包含：表达力覆盖度、AI 可生成性（§C3）、实现复杂度、向后兼容性、可扩展性
- 不限于以下方向但需覆盖其中至少 2 个：
  - 方向 A：扩展现有 manifest.json（新增场景间依赖/顺序字段）
  - 方向 B：新增 lesson-plan 编排层（独立于 scenario 的上层结构）
  - 方向 C：轻量 DSL / 状态机引擎

### 3.3 E3 - 方案推荐

**目标**：给出明确推荐。

**要求**：
- 推荐理由需引用 E2 对比结论
- 需说明推荐方案的风险点和缓解策略
- 需说明推荐方案与 AI 可生成化路线（§C3）的关系——剧本 JSON 结构是否适合 AI 根据 schema + prompt 生成

### 3.4 E4 - PoC 设计（仅设计，不实现）

**目标**：推荐方案的最小可演示设计。

**要求**：
- 提供剧本 JSON 结构示例（至少覆盖 3 种编排模式：线性序列、条件分支、前置解锁）
- 提供核心运行逻辑伪代码（剧本加载 → 当前节点判定 → 节点切换 → 完成判定）
- 标注哪些部分依赖 req-criteria-composable 的条件树、哪些部分依赖 req-predictive-inquiry 的得分能力
- **明确声明**：PoC 设计不包含可运行代码实现

### 3.5 E5 - 工作量估算

**目标**：粗粒度估算，支持立项决策。

**要求**：
- 按"方案级人天"粒度（如：Phase 1 基础编排 X 天、Phase 2 条件分支 Y 天）
- 列出关键假设（如：假设条件树已完成、假设不需要新 UI 等）
- 标注估算置信度（高/中/低）及影响因素

### 3.6 E6 - 前置条件与排期建议

**目标**：明确路线图位置。

**要求**：
- 列出硬性前置条件（必须先完成才能开始）与软性前置条件（并行可行但有风险）
- 给出建议排期位置（相对于 req-criteria-composable / req-predictive-inquiry 的完成时间）

## 4. 验收标准

| # | 验收条件 | 来源 |
|---|---------|------|
| AC1 | 评估报告包含完整的表达力缺口分析，缺口 ≥ 3 类且各带严重程度标注 | S1, S2, S7 |
| AC2 | 评估报告包含 ≥ 2 个候选方案的结构化对比（含 ≥ 5 个对比维度） | S8 |
| AC3 | 评估报告明确推荐一个方案，推荐理由引用对比结论 | S8 |
| AC4 | 推荐方案附带 PoC JSON 结构示例（覆盖线性序列 + 条件分支 + 前置解锁三种模式） | S8 |
| AC5 | 推荐方案附带核心运行逻辑伪代码 | S8 |
| AC6 | 报告包含方案级工作量估算（人天 + 关键假设 + 置信度） | S8 |
| AC7 | 报告包含前置条件依赖图和排期建议 | S8 |
| AC8 | 所有方案均需说明对 §C3 AI 可生成化路线的满足情况 | S3, S8 |
| AC9 | 所有方案均需说明对现有 42 个场景 JSON 的向后兼容策略 | S5 |
| AC10 | 用户已在 process.txt 留下明确的 go / no-go / defer verdict | S8 |

> **AC10 是本需求的最终关闭条件**——报告交付后必须等待用户拍板。

## 5. 约束与假设

### 5.1 硬约束

| # | 约束 | 来源 |
|---|------|------|
| C1 | 本需求**不实现** runtime 代码，产出仅为评估报告 | S1, S8 |
| C2 | 剧本 JSON 设计必须延续 AI 可生成化路线（§C3：prompt + schema + 样本即可生成） | S3, S8 |
| C3 | 必须兼容现有 42 个场景 JSON（不破坏现有场景的独立运行能力） | S5 |
| C4 | 暂不考虑可视化编排 UI（剧本由内容作者手写 + AI 辅助生成） | S8 |
| C5 | 新增编排结构必须走 ScenarioManager 加载体系（§C1 配置化硬约束） | S3 |

### 5.2 假设

| # | 假设 | 影响 |
|---|------|------|
| A1 | req-criteria-composable 将在剧本 runtime 开发前完成（条件树可用） | 若未完成，分支判定能力受限 |
| A2 | req-predictive-inquiry 的得分机制将在剧本 runtime 开发前完成 | 若未完成，"按得分分支"功能需 defer |
| A3 | 评估报告的技术方案设计由 tech-leader 角色负责产出 | PM 只定义评估范围和验收标准 |

## 6. 影响面

### 6.1 本需求直接影响

| 影响对象 | 影响方式 |
|---------|---------|
| 产品路线图 | 评估结论将决定"剧本 runtime"是否进入开发排期 |
| 后续需求 | 若 verdict = go，将拆分为实现型需求（独立 req-id） |

### 6.2 无影响（本需求为纯评估）

- ❌ 不修改现有代码
- ❌ 不修改现有场景 JSON
- ❌ 不影响正在进行的其他需求
- ❌ 不产生用户可感知的功能变化
